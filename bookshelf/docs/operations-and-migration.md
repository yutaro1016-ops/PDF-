# バックアップ・退会・移行の運用案

## 現在できる書き出し
データ管理→フォルダーに保存。Chromium系の対応環境・HTTPS・利用者のフォルダー許可が必要。metadata.json、各PDF、各pages.ndjson、成功時COMPLETE.jsonを出力。途中失敗はCOMPLETEがない未完了バックアップ。書き出し中に変更すると時点整合性が保証されないため操作を止めて実施。対応外端末ではメタデータとPDF個別保存のみで、同等の完全バックアップにならない。
画像/索引/共有含む本番全体の自動バックアップではない。端末の保存先を暗号化しアクセスを限定する。GitHubにPDFや出力データを登録しない。

## ローカル復旧演習
`python3 scripts/restore-backup.py /absolute/backup-folder /absolute/new-recovery-folder`
出力先は存在していてはいけない。完了印、PDFサイズ、索引数を検証し、新規SQLite、PDFコピー、SHA256一覧を生成する。既存本番DB/R2には書き込まない。ユーザーIDはrecovery-stagingであり本番認証IDへの対応を別途確定する必要がある。共有リンク/取り込み途中状態は再作成しない。これは破損バックアップ検出と移行用の検証ステージであり、本番復旧の完了ではない。

## 販売前の復旧体制
プラットフォームが提供する正式なDB全量/R2全量の取得・復旧方法と担当権限を確認する。現在のツールでは本番フルリストアを確認できていない。D1 Time Travelの一般機能をSitesで利用可能と断定しない。別領域のバックアップ、暗号化、保持期間、目標RPO/RTO、復旧担当を決め、独立テスト環境でID/冊数/ファイルハッシュ/索引数/別アカウント分離/検索/共有取消を検証。削除や本番置換は承認後に実施する。

## 退会手順案（未実装）
本人認証→所有冊数・容量と削除範囲を提示→書き出しを提供→明示的確認→本人の共有を取消→進行中取り込み停止→本人R2 PDF/画像と本人DB索引/メタデータ/棚/関連ジョブを削除→監査記録と完了通知。複数サービスに跨る失敗は再実行可能なジョブで追跡する。取り込み済み他人の独立コピーは残ることを事前説明する。バックアップ内データの保持/消去期限も公開する。現時点では退会自動処理を提供していないため販売開始を保留する。

## 容量と監視
現UIは5GBを計画値として表示するだけで強制しない。販売前に登録/共有取り込みの全入口へトランザクションで予約・完了・取消の容量処理を実装。既存超過データを削除せず新規保存制限と猶予案を提示する。PDF以外の索引/画像の計測も費用管理に追加する。
ヘルスAPIはDB/R2到達確認のみ。通知サービス契約はしていない。販売前に外形監視、エラー率/遅延/使用容量の集計と通知、担当者・手順・障害履歴を用意する。問い合わせIDで調査し患者情報/全文/認証トークンをログに含めない。

## 必要になった場合の環境移行
1. 現Sitesの正式なDB/R2エクスポート権限と復旧保証、運用枠/費用を確定。取得できない場合は移行完了を約束しない。
2. 契約・費用の説明と了承後、独立ステージ環境へコピー。旧環境を削除・上書きしない。
3. 既存PDF ID/バイト/本文索引/棚と順序を維持し、ChatGPTユーザーIDと移行先認証の対応を本人確認して決める。
4. 保存・共有更新を一時停止し確定時点のDB/R2スナップショットを取得。帳票の冊数/ハッシュ/検索結果を照合。
5. 実機と複数アカウントの受入、復旧演習、容量/退会/監視を検証後に切り替える。旧URLは現在維持。OpenAI所有サブドメインを別ホストへ移管できると想定せず、旧Siteから案内/リダイレクトの可否を確認する。
6. 旧環境は一定期間読取専用。ロールバック時は新環境の追加データ差分を保全し、単純な切戻しによる消失を防ぐ。
今回、移行・契約・有料支出・既存PDF削除はしていない。

## version18: 実装済み・無効の運用機能
CAPACITY_ENFORCED=true の時だけ5GBを強制。uploading/importing/readyの宣言サイズと、まだbook行のない進行中共有取り込みを合算する。登録INSERTと共有ジョブINSERTに同じSQL内で容量条件を入れ、並行登録の過剰予約を防ぐ。完了時の二重計上を避け、中止/削除で予約を解放する。既存超過データは削除しない。現在はfalseのまま。
ACCOUNT_DELETION_ENABLED=true の時だけ退会処理を許可。ログイン本人の5分期限nonce・確認文・書き出し確認が必要。deleting状態で通常APIを止め、共有を取消、取り込みのleaseを待って停止、10冊ずつR2→DBの順で削除し、本人prefixの残存物と棚/関連行を整理する。停止時は同じ本人・jobで再開。他人の独立コピーには触れない。deletedの最小tombstoneが再登録を防ぐ。現在はfalseのまま。本人再認証の鮮度、長時間進行中upload、期限切れleaseの旧処理、既に中止済みmultipartの再試行、本番保持/消去期限の受入は残課題。これらを検証せず有効化しない。

## バックアップ体制の具体案（未稼働）
目標案: 毎日02:00 JSTにDB/R2の正式な全量取得、RPO24時間、RTO4時間。日次14世代・週次8世代・月次6世代を別の障害領域へ保存し、毎月独立復元演習。取得後に全PDFのSHA256/冊数/索引/棚の一致を確認して完了印を付ける。暗号化は保存先KMSのAES256、転送TLS、鍵をバックアップとは別管理しアクセス権を分離。暗号化済み復元と鍵喪失時の手順も試験。失敗/未実行24時間超過/容量超過を担当者へ通知する。
現在は正式な全量export/recoveryの権限と独立保存先/KMS/通知先が確認できず、自動取得・世代削除・暗号化済み本番バックアップを設定していない。外部契約の費用は承認前に提示する。RPO/RTOは保証値ではない。
対応外ブラウザーにも各本の検索索引NDJSONの保存リンクを追加。設定JSON・PDF・索引を組み合わせられるが、手作業のファイル配置と完了印作成が必要でフォルダーバックアップと同等の自動保証はない。version18フォルダー保存は中断/冊単位再開/サイズ・索引数・元メタデータ変化を検出。変更があれば新規保存を要求する。PDF内容の同サイズ改ざん検出や本番一時点スナップショットではない。

## 監視と通知
scripts/health-check.py は公開ヘルスAPIのDB/R2到達のみを判定し、本文やPDF IDを記録しない。GitHub Actionsの主要チェックに追加し、失敗時はWorkflow failureとGitHub標準通知の対象になる。ただし受信設定と通知到達は未確認。外部通知サービスは契約していない。定期監視案は15分毎、連続2回で一次対応、復旧後に状況確認。default branchへレビュー済みworkflowを反映するまで定期実行は稼働しない。
通知受信後: 公開範囲/DB/R2の疎通を確認→問い合わせIDでログを調査→新規書込を止める必要性を判断→復旧/ロールバックを実施→データ差分照合→再発防止記録。コードのデプロイ成功はPDFの動作保証にしない。

## GitHubとビルド・公開
bookshelf/配下に全アプリソース・lockfile・build helperを保存。PDF.jsの200資産は既存同版npm tarballから scripts/prepare-pdf-vendor.py で再現し、tarballと各ファイルのSHA256を照合する。機密データは入れない。取得は開発/ビルド時だけで、公開アプリはローカル資産を使う。
手順: cd bookshelf → npm run install:ci → python3 scripts/prepare-pdf-vendor.py → npm run build。Sitesへの公開は同じプロジェクトの認証済みソース保存→ビルド済みarchiveの保存→同じURLへデプロイ。GitHub ActionsだけでSites公開する正式なサービス資格情報/APIは未確認で自動公開は未設定。公開版のSitesソースSHAとGitHub commitを照合記録する。
ロールバック: version17の保存済みarchive付き版へ再デプロイ。追加のaccount_lifecycleテーブルを削除せず残す（既存データ変更なし）。容量/退会を有効化した後は旧版が停止状態を無視するため単純にversion17へ戻さず互換修正版で対応する。本番DB/PDFを古いバックアップで上書きしない。

## version19候補の継続記録
正式な本番全量export/recoveryポイント/保持期間/サービス資格情報は引き続き確認できず、独立した本番全量復元・自動暗号化取得は実行していない。運営元への質問と必要権限、監視通知の受信手順/費用条件はplatform-confirmation-request.mdを参照。問い合わせ送信、外部契約、cron有効化、自動公開設定、環境切替は行っていない。
