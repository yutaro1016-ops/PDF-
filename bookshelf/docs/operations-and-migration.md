# バックアップ・退会・移行の運用案

## 現在できる書き出し
データ管理→フォルダーに保存。Chromium系の対応環境・HTTPS・利用者のフォルダー許可が必要。metadata.json、各PDF、各pages.ndjson、成功時COMPLETE.jsonを出力。途中失敗はCOMPLETEがない未完了バックアップ。書き出し中に変更すると時点整合性が保証されないため操作を止めて実施。対応外端末ではメタデータとPDF個別保存のみで、同等の完全バックアップにならない。
画像/索引/共有含む本番全体の自動バックアップではない。端末の保存先を暗号化しアクセスを限定する。GitHubにPDFや出力データを登録しない。

## ローカル復旧演習
`python3 scripts/restore-backup.py /absolute/backup-folder /absolute/new-recovery-folder`
出力先は存在していてはいけない。完了印、PDFサイズ、索引数を検証し、新規SQLite、PDFコピー、SHA256一覧を生成する。既存本番DB/R2には書き込まない。ユーザーIDはrecovery-stagingであり本番認証IDへの対応を別途確定する必要がある。共有リンク/取り込み途中状態は再作成しない。これは破損バックアップ検出と移行用の検証ステージであり、本番復旧の完了ではない。

## 販売前の復旧体制
プラットフォームが提供する正式なDB全量/R2全量の取得・復旧方法と担当権限を確認する。現在のツールでは本番フルリストアを確認できていない。D1 Time Travelの一般機能をSitesで利用可能と断定しない。別領域のバックアップ、暗号化、保持期間、目標RPO/RTO、復旧担当を決め、独立テスト環境でID/冊数/ファイルハッシュ/索引数/別アカウント分離/検索/共有取消を検証。削除や本番置換は承認後に実施する。

## 退会手順案（未実装）
本人認証→所有冊数・容量と削除範囲を提示→書き出しを提供→明示的確認→本人の共有を取消→進行中取り込み停止→本人R2 PDF/画像と本人DB索引/メタデータ/棚/関連ジョブを削除→監査記録と完了通知。複数サービスに跨る失敗は再実行可能なジョブで追跡する。取り込み済み他人の独立コピーは残ることを事前説明する。バックアップ内データの保持/消去期限も公開する。現時点では退会自動処理を提供していないため販売開始を保留する。

## 容量と監視
現UIは5GBを計画値として表示するだけで強制しない。販売前に登録/共有取り込みの全入口へトランザクションで予約・完了・取消の容量処理を実装。既存超過データを削除せず新規保存制限と猶予案を提示する。PDF以外の索引/画像の計測も費用管理に追加する。
ヘルスAPIはDB/R2到達確認のみ。通知サービス契約はしていない。販売前に外形監視、エラー率/遅延/使用容量の集計と通知、担当者・手順・障害履歴を用意する。問い合わせIDで調査し患者情報/全文/認証トークンをログに含めない。

## 必要になった場合の環境移行
1. 現Sitesの正式なDB/R2エクスポート権限と復旧保証、運用枠/費用を確定。取得できない場合は移行完了を約束しない。
2. 契約・費用の説明と了承後、独立ステージ環境へコピー。旧環境を削除・上書きしない。
3. 既存PDF ID/バイト/本文索引/棚と順序を維持し、ChatGPTユーザーIDと移行先認証の対応を本人確認して決める。
4. 保存・共有更新を一時停止し確定時点のDB/R2スナップショットを取得。帳票の冊数/ハッシュ/検索結果を照合。
5. 実機と複数アカウントの受入、復旧演習、容量/退会/監視を検証後に切り替える。旧URLは現在維持。OpenAI所有サブドメインを別ホストへ移管できると想定せず、旧Siteから案内/リダイレクトの可否を確認する。
6. 旧環境は一定期間読取専用。ロールバック時は新環境の追加データ差分を保全し、単純な切戻しによる消失を防ぐ。
今回、移行・契約・有料支出・既存PDF削除はしていない。
